# Bocchi 実装計画書（プロトタイプ）

- 作成日: 2026-07-08
- 前提: 開発者 1 人による個人開発・プロトタイプ実装。リリース日は未定のため、日付ベースのスケジュールではなく**マイルストーン駆動**（動くものが段階的に増える単位）で計画する
- 参照: `docs/product-discovery.md`（企画）、`docs/interview-decisions.md`（D1〜D8。本計画書は D1〜D8 に厳密に従う）
- 位置づけ: 本スキル（project-planning）の標準テンプレートのうち、個人開発では過剰になる要素（RACI 表・3 点見積もり・定例会議体等）は簡略化し、マイルストーン分解・タスク分解・リスク検証・実地検証チェックリストに重点を置く

---

## 1. 目的とゴール

- 背景: 懇親会で孤立する参加者を、同じ状況の人同士でつなぐ Web アプリを作り、実際のイベントに投入して行動仮説・密度仮説を検証する（`docs/product-discovery.md` 5節）
- 目的: 「作ること自体が個人開発のモチベーション」（D1）である前提のもと、実装を通じて Supabase を学習しつつ、実地検証に耐える最小限の動く製品を作る
- ゴール（完了の定義）: 以下をすべて満たした状態を「プロトタイプ完成」とする
  1. D2〜D7 で確定した MVP 機能（イベント入室、ルーム作成・一覧、ロビー自動マッチ、ルームチャット、話題カード、24 時間 TTL）が、Vercel + Supabase の本番相当環境で一連の流れとして動作する
  2. スマートフォン実機・モバイル回線で一通りの操作が完了できる
  3. 「9. 実地検証前のチェックリスト」を満たし、実際の懇親会に投入できる状態にある

## 2. スコープ

### スコープに含むもの（MVP = v1、D7 準拠）

- イベント入室: URL/QR での入室、ハッシュタグ名手入力での入室（存在しなければ自動作成 = upsert）、入力正規化、類似イベントのサジェスト（D2）
- ルーム作成: 定員指定（デフォルト 3 人、2〜6 人で変更可）、1 人でも作成・入室可能（D5）
- ルーム一覧: 能動的にルームを選んで入室できる導線（D3）
- ロビー待機 → 自動マッチング: 待機人数の表示、60〜90 秒での自動マッチング、「空きのある既存ルーム優先 → なければ新ルーム」の優先順（D3）
- ルームチャット: マッチ成立時のシステム自動投稿、クイック返信候補（D4）
- 話題カード（アイスブレイク支援）（D7）
- イベント・ルームの 24 時間自動期限切れ（D7）
- ニックネームのみでの入室（端末ローカル保存）、任意の X アカウント欄（D6）

### スコープに含まないもの（意図的にやらないこと。9 節も参照）

- Web Push 通知（D7 で明示的に見送り。気づきは画面内表示・音・バイブで代替）
- 通報・ブロック機能（D7 で明示的に見送り）
- ログイン・アカウント登録・OAuth 認証（D6 の決定。なりすましリスクは受容）

## 3. 進め方・体制

- 開発者 1 人による個人開発。PM／設計／実装／検証をすべて 1 人で兼務するため、RACI 表・承認フロー・定例会議体は設けない
- 意思決定の記録は本計画書と `docs/interview-decisions.md` に集約し、途中で前提が変わった場合はこれらを更新してから作業を進める
- タスク管理は GitHub Issue またはチェックリスト（本計画書 6 節）で行い、「完了/未完了」の二値で進捗を測る（10 節）

## 4. アーキテクチャ方針

`docs/interview-decisions.md` D8 の移植性要件（「Supabase 依存はアダプター層に隔離し、UI・ドメインロジックはインターフェース越しに使う。差し替え時の書き直しがアダプター層だけで済むこと」）を実装レベルに落とし込む。

### ディレクトリ構成案

```
src/
  app/                      … Next.js App Router（画面・Route Handler）
  lib/
    domain/
      interfaces/           … EventRepository, RoomRepository, LobbyRepository,
                               ChatRepository, RealtimeChannel などのインターフェース定義
      services/              … マッチング判定ロジック等、Supabase 非依存の純粋関数
    adapters/
      supabase/              … Supabase 依存を閉じ込める実装（Repository 実装、Realtime 購読）
    local/                   … 端末ローカル保存（ニックネーム・端末識別子）
  components/                … UI コンポーネント（ドメイン層・アダプター層に直接依存しない）
supabase/
  migrations/                … 素の SQL マイグレーション（Supabase CLI の規約ディレクトリ。標準 Postgres SQL で記述）
```

- UI・ドメインロジックは `lib/domain/interfaces/` のインターフェース越しにのみデータ操作を行い、`lib/adapters/supabase/` の実装を直接 import しない
- マッチング判定ロジック（誰をどのルームに割り当てるか）は Supabase に依存しない純粋関数として `lib/domain/services/` に置き、「いつ実行するか（トリガー）」の部分だけをアダプター層で差し替え可能にする（7 節 R4 参照）
- スキーマは Supabase のマイグレーション UI ではなく、素の SQL ファイル（`supabase/migrations/`）で管理し、標準 Postgres として持ち出せる状態を保つ

### 主要テーブル案（詳細はスキーマ設計タスクで確定）

| テーブル        | 用途                         | 主な列（例）                                                             |
| --------------- | ---------------------------- | ------------------------------------------------------------------------ |
| `events`        | イベント（ハッシュタグ単位） | id, slug, display_name, normalized_name, created_at, expires_at          |
| `rooms`         | ルーム                       | id, event_id, name, capacity, status, created_at, expires_at             |
| `room_members`  | ルーム参加者                 | id, room_id, nickname, x_account, device_id, joined_at                   |
| `lobby_entries` | ロビー待機者                 | id, event_id, nickname, device_id, entered_at, matched_room_id           |
| `messages`      | ルームチャット               | id, room_id, sender_type(system/user), sender_nickname, body, created_at |
| `topic_cards`   | 話題カードのお題             | id, category, prompt_text                                                |

- `device_id`: 認証なしのため、端末ローカルで発行した識別子を各操作に添付し「自分の発言・自分の参加」を識別する（なりすまし対策はしない前提を D6 通り受容）

### 主要インターフェース例（命名イメージ。実装コードはここでは書かない）

- `EventRepository`: `findBySlug()`, `upsertByName()`, `searchSimilar()`
- `RoomRepository`: `list()`, `create()`, `join()`, `leave()`, `getWithMemberCount()`
- `LobbyRepository`: `enqueue()`, `dequeue()`, `listWaiting()`
- `ChatRepository`: `listMessages()`, `postMessage()`
- `RealtimeChannel<T>`: `subscribe(onEvent)`, `unsubscribe()`
- `MatchingService`（ドメイン層・純粋関数）: `decideMatch(waitingEntries, openRooms, capacityRule): MatchResult`

## 6. マイルストーンごとのタスク分解

各タスクは「担当 1 名（自分）に割当可能」な粒度まで分解している。厳密な工数見積もり（PERT 等）は個人開発の性質上省略し、着手順序と完了条件のみを管理する。

### M0: プロジェクトセットアップ

- Next.js（App Router・TypeScript）プロジェクトの作成（Docker なし・ホストで直接起動）
- ローカル Supabase 環境の構築（Supabase CLI + Docker。`supabase init` / `supabase start` で完結）
- `src/lib/domain/` `src/lib/adapters/supabase/` を含むディレクトリ構成の確定（4 節）
- 素の SQL マイグレーション運用方法の確立（`supabase/migrations/` の命名規則、適用コマンドの確認）
- Lint / Format（ESLint・Prettier 等）の設定
- 環境変数管理（`.env.local` にローカル Supabase の URL/anon key。クラウド用の値は開発者が後で差し替え）
- ローカル Supabase への疎通確認用の最小ページ実装

※ Vercel プロジェクト作成・自動デプロイ・クラウド Supabase（無料枠）の作成と疎通は開発者自身が手動で行う。実装は環境変数の差し替えだけでクラウドに向けられる状態を保つこと。

### M1: 入室〜ルーム一覧の縦切り

- スキーマ設計: `events` `rooms` `room_members` のマイグレーション SQL 作成
- ドメイン層インターフェース定義: `EventRepository`, `RoomRepository`
- アダプター層実装: `SupabaseEventRepository`, `SupabaseRoomRepository`
- ハッシュタグ正規化ロジックの実装（ドメイン層の純粋関数。小文字化・全角半角統一・記号統一 ※具体ルールは R5 で先行検証）
- 類似イベントサジェストの実装（方式は R5 の検証結果に従う）
- 画面: イベント入室画面（URL/QR パラメータでの入室、ハッシュタグ手入力 → upsert）
- 画面: ルーム一覧画面（定員・現在人数の表示）
- 画面: ルーム作成画面（定員 2〜6 人指定、1 人でも作成可）
- ニックネーム入力・端末ローカル保存（`device_id` 発行含む）の実装
- イベント共有用 QR コードの生成
- 開発方針の確認: サーバー経由でのみ Supabase にアクセスする構成（R2）をこの段階で確立する

### M2: ロビー自動マッチ

- スキーマ追加: `lobby_entries` のマイグレーション SQL 作成
- ドメイン層: `MatchingService.decideMatch()`（Supabase 非依存の純粋関数）の実装
- マッチング実行トリガー方式の決定・実装（R4 の検証結果に従う。Edge Function + pg_cron / Vercel Cron / クライアント主導のいずれか）
- 同時実行時の競合制御実装（トランザクション・一意制約等。R3 の検証結果に従う）
- ドメイン層インターフェース定義・アダプター実装: `LobbyRepository`
- 画面: ロビー待機画面（待機人数のリアルタイム表示、待機時間の目安表示）
- リアルタイム購読: ロビー人数更新（Supabase Realtime、R1 の検証結果に従う）
- マッチ成立後のルーム画面への自動遷移

### M3: ルームチャット

- スキーマ追加: `messages` のマイグレーション SQL 作成
- ドメイン層インターフェース定義: `ChatRepository`, `RealtimeChannel`
- アダプター実装: メッセージ送受信・Realtime 購読（Postgres Changes か Broadcast かは R1 の検証結果に従う）
- マッチ成立時のシステム自動投稿ロジック（M2 のマッチング成立と連携）
- クイック返信候補（定型文タップ送信）の実装
- 画面: ルームチャット画面（メッセージ一覧・入力欄・クイック返信）

### M4: 話題カード・TTL・磨き込み

- 話題カードのお題データ設計（テーブル or 静的データ。お題の中身は interview-decisions.md の未決事項につき別途決定）
- 画面: 話題カード表示・再抽選 UI
- TTL: イベント・ルームの 24 時間自動期限切れ実装（まず論理非表示、物理削除は R6 の検証結果に従い後回し可）
- マッチ成立時の気づき演出（画面内の目立つ表示・音・バイブ）の実装
- 全体 UI の磨き込み（モバイル操作性、エラー表示、通信断時の挙動）

### M5: 実地検証準備

- 9 節のチェックリストの実施
- 複数端末での同時アクセス・同時マッチングの模擬テスト
- Supabase/Vercel 障害時の最低限のフォールバック表示の確認
- 実地検証当日の運用手順（QR 掲示方法・案内文言）の準備

## 7. 技術的リスクと先行検証項目

各リスクは、関連するマイルストーンの着手前に検証し、結果を実装方針に反映する。

| #   | リスク／検証項目                 | 内容                                                                                                                          | 検証タイミング         | 対応方針                                                                                                                                                                                                      |
| --- | -------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- | ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| R1  | Supabase Realtime の挙動         | 無料枠の同時接続数上限、Postgres Changes と Broadcast の使い分け、モバイル回線でのネットワーク切替時の再接続挙動              | M2 着手前              | 小規模な疎通実験（別タブ・別端末での購読テスト）を先に行い、チャットとロビー更新の両方の要件を満たせるか確認する                                                                                              |
| R2  | 匿名アクセスと RLS 設計          | 認証なしで Supabase にどうアクセスするか（クライアントから直接 vs サーバー経由）。不正な書き込みの防止                        | M1 着手前              | サーバー（Route Handler / Server Action）経由でのみ DB 操作する方式を軸に検証する。クライアントに Service Role キーを渡さず、アダプター層のみが Supabase にアクセスする構成とし、RLS はシンプルな構成に留める |
| R3  | 同時マッチングの競合制御         | 複数の待機者がほぼ同時にマッチング判定された場合の二重割当防止                                                                | M2 着手前              | トランザクション・一意制約・行ロックによる排他制御を検証する。実行主体をできるだけ 1 本化する設計を優先検討する                                                                                               |
| R4  | マッチング実行トリガーの置き場所 | 定期実行の仕組み（Edge Function + pg_cron、Vercel Cron、クライアント主導）の比較                                              | M2 着手前              | 無料枠での実現性とアダプター層隔離の両立を優先する。判定ロジックは純粋関数のまま、実行トリガーのみ差し替え可能な形に設計する                                                                                  |
| R5  | ハッシュタグ正規化・類似検索     | 正規化ルールの具体化（記号・絵文字の扱い等）、類似サジェストの実装方式                                                        | M1 着手前              | Postgres の `pg_trgm` 拡張が Supabase で利用可能か確認する。利用できない場合はアプリ側での簡易な類似度計算（レーベンシュタイン距離等）に切り替える                                                            |
| R6  | TTL 自動期限切れの実装方式       | 定期削除ジョブの実行方式、物理削除と論理非表示のどちらを先に実装するか                                                        | M4 着手前              | まず `expires_at` によるフィルタ（論理非表示）を実装し、物理削除の仕組みは後回しにする                                                                                                                        |
| R7  | Vercel / Supabase 無料枠の制約   | 帯域・関数実行時間・DB 接続数等の上限が、実地検証時の想定同時利用規模（数十人）で足りるか                                     | M5 着手前              | 想定規模での概算を行い、無料枠を超過しそうな場合は利用時間の限定など事前の対応策を用意する                                                                                                                    |
| R8  | ドメイン／アダプター境界の実効性 | 「差し替えはアダプター層だけで済む」という目標水準を保てているか。Supabase 固有の型・クエリがドメイン層や UI に漏れていないか | 各マイルストーン完了時 | マイルストーン完了ごとに、ドメイン層・UI がインターフェース経由でのみデータ操作しているかをセルフレビューする                                                                                                 |

## 8. 進捗の測り方

- 個人開発のため定例報告は設けないが、進捗の自己申告（体感 %）には頼らない
- 6 節の各タスクをチェックリスト（または GitHub Issue）単位に分解し、「完了/未完了」の二値でカウントする
- マイルストーンは、5 節に定めた完了条件（実際に動作確認できる状態）を満たした時点でクローズしたとみなす
- マイルストーンをクローズしたら、`AGENTS.md` の「今後の方針」に沿って開発コマンド・ディレクトリ構成・データフローの記載を追記していく

## 9. 実地検証（懇親会投入）前のチェックリスト

- [ ] M0〜M4 のマイルストーン完了条件をすべて満たしている
- [ ] Vercel + Supabase の本番相当環境で、入室 → ルーム作成/ロビー → マッチ → チャット → 退出までの一連の流れを通しで動作確認済み
- [ ] スマートフォン実機（複数台・複数 OS）で動作確認済み
- [ ] モバイル回線（Wi-Fi ではない 4G/5G 環境）での動作・再接続を確認済み
- [ ] QR コード／共有 URL の現地掲示物・案内文言を準備済み
- [ ] 会場の Wi-Fi 事情・通信混雑を想定し、代替の入室導線（URL の口頭案内等）を用意している
- [ ] 24 時間 TTL が実地検証イベントの開催時間より十分長いことを確認済み
- [ ] 想定最大同時接続数でのロビー自動マッチングを模擬テスト済み（二重割当が起きないこと）
- [ ] Supabase／Vercel の利用量ダッシュボードで無料枠の残量を確認済み
- [ ] 通信断・Supabase 障害時にユーザーが操作不能なまま詰まらない、最低限のフォールバック表示がある
- [ ] 主催者への事前確認・告知（QR 掲示の許可、案内文言のレビュー）が済んでいる
- [ ] 成功基準（暫定案: 1 イベントで「ひとりです」相当の利用 10 人以上、合流率 50% 以上。`docs/product-discovery.md` 5 節、`docs/interview-decisions.md` 未決事項につき最終確認要）の計測方法（何をどう数えるか）を決めている
- [ ] 検証後の振り返り方法（当日使わなかった/動けなかった参加者へのヒアリング等）を決めている

## 10. 意図的にやらないことリスト

D7 の明示的な見送り事項に加え、プロトタイプとして今回のスコープ外とするものを整理する。

- Web Push 通知（D7。気づきは画面内表示・音・バイブで代替、画面を開いたまま待つ前提）
- 通報・ブロック機能（D7。小規模利用のためリスク低と判断し、規模が出たら再検討）
- ユーザー認証・アカウント登録（OAuth・パスワード等）（D6。ニックネームのみ、なりすましリスクは受容）
- ネイティブモバイルアプリ化（Web のみ）
- 多言語対応（日本語のみ）
- 主催者向け管理画面・利用状況分析ダッシュボード
- 決済・課金機能
- チャットへの画像・ファイル添付
- 話題カードの高度なレコメンド（当面は固定リストからのランダム/簡易提示に留める）
- 自動テストの網羅的整備・本格的な CI/CD（プロトタイプのため lint・型チェック程度に留め、動作確認は手動を中心とする）
- 詳細な監視・アラート基盤（Vercel/Supabase の標準ダッシュボード確認で代替する）
- 会議体・承認フロー等の正式なプロジェクト管理プロセス（個人開発のため不要）
