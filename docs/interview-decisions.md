# Bocchi 設計インタビュー決定事項

- 作成日: 2026-07-07
- 経緯: `docs/product-discovery.md` の計画を対象に実施した設計インタビューの結果。本文書の決定は discovery 文書の MVP 案（手動検証先行）を上書きする。

## 決定事項

### D1. 進め方: 最小 Web アプリを先に作って実地検証する

手動検証（X 告知＋目印）は行わず、最小の Web アプリを実装して次に参加するイベントの懇親会に投入する。作ること自体が個人開発のモチベーションであるため。行動仮説が外れた場合に実装分が無駄になるリスクは受容する。

### D2. イベント入室: ハッシュタグ風の名前＋「なければ自動作成」（upsert）

- 入室の主経路は共有 URL / QR コード。X などにリンクを流し、タップで入室
- ハッシュタグ名の手入力でも入室でき、存在しなければその場で自動作成される
- 表記ゆれによるイベント分裂（密度仮説の自壊）を防ぐため、以下を必須とする:
  - 入力の正規化（小文字化・全角半角統一・記号の統一）をしてから照合
  - 新規作成前に類似名のイベントをサジェストし、既存への合流を促す

### D3. マッチング構造: ルーム選択＋ロビー自動マッチの二段構え

- イベント内に複数の「ルーム」（トークグループ）が存在する
- ルームは誰でも作成でき、**1 人でも作成して入室できる**（最初の 1 人が受け皿になる）
- 能動的な人はルーム一覧から選んで入室できる
- 受動的な人はロビーで待機し、一定時間経過で自動マッチング
- 自動マッチングの優先順: ①空きのある既存ルームへ割り当て → ②なければロビー待機者同士で新ルームを作成
- ロビーには待機人数を表示し、1 人でルームを作った人にも「ロビーに◯人待機中」を見せる

### D4. 物理合流: ルーム内チャットで相談して合流する

- マッチ成立でルーム内チャットが開く
- 「チャットで止まる」対策として、成立時に**システムが最初のメッセージを自動投稿**する
  （集合場所の相談を促す文＋タップで答えられるクイック返信候補）

### D5. グループサイズ: ルーム作成時に指定可能

- デフォルト 3 人、作成者が 2〜6 人の範囲で変更できる
- 自動マッチングはルームの定員（空き）を尊重する

### D6. 識別・認証: ニックネームのみ・登録不要＋任意の X アカウント欄

- ログイン・アカウント登録なし。ニックネーム入力で即入室（端末ローカルに保存）
- 希望者はプロフィールに X アカウントをテキストで添えられる（OAuth なし。なりすましリスクは受容）

### D7. MVP（v1）の機能範囲

コア体験（D2〜D6）に加えて含めるもの:

- **部屋・イベントの自動期限切れ**（作成から 24 時間で消滅。古い部屋の混乱とデータ残留を防ぐ）
- **話題カード**（アイスブレイクのお題提示）

v1 で見送るもの:

- Web Push 通知（マッチ成立の気づきは、画面内の目立つ表示・音・バイブで代用。画面を開いたまま待つ前提）
- 通報・ブロック（小規模利用のためリスク低と判断。規模が出たら再検討）

### D8. 技術スタック: Next.js + Supabase（乗り換え可能な作りにする）

- Supabase は未経験だが学習目的込みで採用。Vercel + Supabase の無料枠で運用
- リアルタイム（チャット・ロビー更新・マッチ通知）は Supabase Realtime を使う
- **移植性の要件**: Supabase 依存はアダプター層（例: `src/lib/adapters/`）に隔離し、UI・ドメインロジックはインターフェース越しに使う。スキーマは素の SQL マイグレーションで管理（標準 Postgres として持ち出せるように）。目標水準は「差し替え時の書き直しがアダプター層だけで済む」こと

## 仮置きのデフォルト値（設定で変更可能にする。実地検証で調整）

| 項目                       | 仮の値                |
| -------------------------- | --------------------- |
| イベント・ルームの TTL     | 作成から 24 時間      |
| ロビー自動マッチの待ち時間 | 60〜90 秒             |
| ルーム定員のデフォルト     | 3 人（2〜6 で変更可） |

## 未決事項（次回確認）

- **最初の実地検証の場**: 参加予定イベントの有無・時期が未回答。推奨は「数十人規模の勉強会の懇親会でまず試す」（協力を頼みやすく、密度仮説の成立条件 5 人を作りやすい）。ここが決まるとリリース目標日が決まる
- 話題カードのお題の中身（技術ネタ中心か、一般ネタ混在か）
- ハッシュタグ正規化の具体ルール（記号の扱いなど、実装時に確定）
- 成功基準の最終確認（discovery 文書の案: 1 イベントで「ひとりです」相当の利用 10 人以上・合流率 50% 以上）
