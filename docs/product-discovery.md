# Bocchi プロダクトディスカバリー（企画・課題仮説整理）

- 作成日: 2026-07-07
- 前提: 個人開発（無料・自分の課題解決が起点）／ターゲットは懇親会が苦手な参加者本人／国内の技術カンファレンス・勉強会中心
- 位置づけ: 開発着手前の事業（企画）仮説の点検。金銭的な収益化は目的としないため、市場規模は金額ではなく「潜在ユーザー数」で概算する

---

## 1. 課題仮説シート

- **ターゲット顧客**: 国内の技術カンファレンス・勉強会に参加する、人見知り・初参加のITエンジニア。本編には満足しているが、懇親会では知り合いがおらず輪に入れない層
- **課題**: 懇親会で話しかけるきっかけと相手が見つからず、孤立したまま時間を過ごす（あるいは早々に帰る・そもそも懇親会を欠席する）
- **その課題が起きる状況（ジョブ）**: 本編終了後、懇親会開始直後。既に知り合い同士の輪ができあがっており、単身参加者は入るタイミングを失う。乾杯後 15〜30 分が最もつらい時間帯
- **現在の代替手段**:
  - 気合いで話しかける／輪に「入ってもいいですか」と言う
  - スタッフ・登壇者として参加し、役割で会話のきっかけを作る
  - X(Twitter) のイベントハッシュタグで交流し、オンラインからリアル合流を狙う
  - 壁際でスマホを見てやり過ごす／懇親会に出ない
- **代替手段の不満**:
  - 話しかけるのは心理的ハードルが最も高く、それができないからこの課題がある
  - スタッフ・登壇はぼっち回避に有効だが、準備コストが大きく毎回は取れない手段
  - ハッシュタグ交流は「会場内のどこにいる誰か」まで特定できず、リアル合流に接続しにくい
- **課題の深刻度**: **中〜高**。イベント参加のたびに発生（頻度: 高）。「懇親会がつらいので参加しない」という行動変化まで起こしている（痛み: 中〜高）。コミュニティ内で「#ぼっち対策会議」と題した勉強会資料や対策ブログが多数存在することが、課題の実在の傍証
- **この仮説が正しいと言える前提条件（最も危うい前提）**:
  1. **行動仮説**: ぼっち状態の人が、その場でアプリを開いて「見知らぬ人と合流する」行動を実際に取るか（話しかけられない人が、アプリ経由なら動けるのか）
  2. **密度仮説**: 同一の懇親会会場に同時ユーザーが一定数（目安 5 人以上）いないと価値がゼロになる。この初期密度を個人開発の告知力で作れるか

## 2. リーンキャンバス

| ブロック                 | 記入内容                                                                                                                                                       |
| ------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| (1) 顧客セグメント       | 国内技術カンファレンス・勉強会の単身参加者。アーリーアダプター: 人見知りを自覚し、X で技術コミュニティを追っているエンジニア（作者自身を含む）                 |
| (2) 課題                 | ①懇親会で話し相手が見つからず孤立する ②輪に入るきっかけがない ③誰が「話しかけて OK な人」か分からない。代替手段: 気合い／スタッフ化／X ハッシュタグ／我慢      |
| (3) ソリューション       | ①イベントコードで入室し「今ひとりです」を発信 → 同じ状態の人を提示・合流させる ②集合場所（ぼっち避難所）の提示 ③興味タグ・話題カードによるアイスブレイク支援   |
| (4) 独自の価値提案 (UVP) | 「話しかけられない人見知りが、同じ〈今ひとりの人〉と合流できる、懇親会ぼっち回避アプリ」— 社交的になるためのツールではなく、ぼっち同士をつなぐ当事者目線       |
| (5) 収益の流れ           | なし（無料・個人開発）。将来の可能性としてスポンサー・主催者課金があり得るが現時点では対象外                                                                   |
| (6) 圧倒的な優位性       | 【仮説】作者自身が当事者である開発姿勢と、「ぼっちアプリ」というネタ性による口コミ拡散力。同一イベント内ユーザー密度が上がればネットワーク効果が働く（未検証） |
| (7) コスト構造           | サーバー・ドメイン代（月数百〜数千円）と開発時間。金銭リスクはほぼゼロ、最大のコストは開発者の可処分時間                                                       |
| (8) 主要指標             | ①同一イベントでの同時アクティブユーザー数（密度）②「ひとりです」発信 → 実際に合流できた率（マッチ成立率）③次イベントでの再利用率                               |
| (9) チャネル             | X(Twitter) の技術コミュニティ、カンファレンス LT 登壇（アプリ自体をネタに）、connpass イベントページ、自分が参加するイベントでのドッグフーディング             |

## 3. 市場規模（潜在ユーザー数ベース）

無料の個人開発のため金額換算はせず、「どれだけの人に届き得るか」の当たり付けとして概算する。

| 指標 | 定義                                                  | 概算値         | 算出根拠（数式・仮定）                                                                                                               |
| ---- | ----------------------------------------------------- | -------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| TAM  | 国内で技術イベントに年 1 回以上参加する IT エンジニア | 約 30 万人     | 国内 IT 技術者約 100 万人（IPA 等の統計オーダー）× イベント参加経験率 30%（仮定。connpass 会員規模が数十万〜100 万であることと整合） |
| SAM  | うち懇親会に参加し、ぼっち不安を感じる層              | 約 7〜8 万人   | TAM × 懇親会参加率 50%（仮定）× 人見知り・孤立経験の自覚率 50%（仮定）                                                               |
| SOM  | 3 年で現実的に届く範囲（個人開発の告知力）            | 数百〜3,000 人 | 年間 10〜20 イベントで利用 × 1 イベントあたり 10〜50 人 × 口コミ係数。1 イベント内の「密度」が成立するかが上限を決める               |

**点検**: TAM > SAM > SOM の大小関係は妥当。個人開発としては SOM（数百人が実際に助かる）だけでも目的（自分と同類の課題解決）は達成できる構造。

## 4. 競合分析

直接競合（「懇親会ぼっち回避」を参加者本人向けに解く無料アプリ）は調査時点で確認できなかった。近接領域は主催者導入型のイベントネットワーキング SaaS と、ツールを使わない代替手段。

| 観点               | Bocchi（想定）                   | Whova / Brella                                         | EventHub                         | X ハッシュタグ交流               | スタッフ・登壇者化（代替手段） |
| ------------------ | -------------------------------- | ------------------------------------------------------ | -------------------------------- | -------------------------------- | ------------------------------ |
| ターゲット         | 参加者本人（人見知り）           | 主催者（海外・大規模カンファ中心）                     | 主催者（国内 BtoB イベント中心） | 参加者本人                       | 参加者本人                     |
| 導入の主体         | 参加者が単独で利用可             | 主催者の導入が必須                                     | 主催者の導入が必須               | 不要                             | 不要（ただし主催者との調整要） |
| 当日その場の合流   | ◎ 中核機能（「今ひとりです」）   | △ 事前マッチング・チャットが中心                       | △ 名刺交換・面談予約が中心       | △ 位置・タイミングが合わせにくい | ◎ 役割が会話を生む             |
| アイスブレイク支援 | ○ 話題カード（構想）             | △                                                      | △                                | ×                                | ○                              |
| 価格               | 無料                             | 主催者課金（高額）                                     | 主催者課金                       | 無料                             | 無料（時間コスト大）           |
| 強み               | 心理的ハードルの低さ・当事者目線 | 機能網羅・実績                                         | 国内実績・主催者向け機能         | 手軽・既存習慣                   | 確実にぼっち回避できる         |
| 弱み・不満点       | ユーザー密度ゼロだと無価値       | 参加者は主催者が導入しないと使えず、ぼっち救済は目的外 | 同左                             | リアル合流に接続しにくい         | 毎回は使えない・準備コスト大   |

**空白（差別化の余地）**: 「主催者に依存せず、参加者本人が、当日その場で使える」× 「社交強者向けの人脈形成ではなく、ぼっちの救済に特化」という象限には誰もいない。

### ポジショニングマップ

軸は購買（利用）決定要因である「誰が導入するか」と「いつの交流を支援するか」。

```
                    当日その場の合流
                          │
                          │  ★ Bocchi(想定)
   スタッフ化(代替)        │
──────────────────────────┼──────────────────────────
 主催者の導入が必要        │        参加者が単独で使える
                          │
   EventHub / Whova       │  X ハッシュタグ交流
                          │
                    事前の人脈形成・ネットワーキング
```

## 5. 最も危うい前提と検証設計（MVP）

キャンバス全体で「これが崩れたら成立しない」前提は次の 2 つ。

1. **行動仮説（最優先）**: 懇親会でぼっち状態の人は、アプリを使って見知らぬ人と実際に合流する。
   - リスク: 「話しかけられない人」は「アプリで呼ばれても動けない」可能性がある。課題は実在しても、この解決策が行動につながらないかもしれない。
2. **密度仮説**: 同一懇親会に同時ユーザーを 5 人以上集められる。
   - リスク: コールドスタート。0〜2 人ではプロダクトの価値を一度も体験してもらえない。

> **2026-07-07 更新**: 設計インタビューの結果、下記 MVP 案のうち「手動運用（1.）」は行わず、最小 Web アプリを先に作って実地検証する方針に決定した（作ること自体が個人開発の目的であるため）。確定した設計は `docs/interview-decisions.md` を参照。

### MVP 案（フル開発しない）

- **手段**: コンシェルジュ型＋最小 Web の組み合わせ。
  1. 自分が参加する次のカンファレンス懇親会で、X で「#(イベント名)ぼっち」的な告知と集合の目印（ステッカー・テーブル札など主催者に相談）を手動運用してみる — アプリなしで行動仮説だけを検証
  2. 反応があれば、1 画面だけの Web アプリ（イベントコード入力 →「今ひとりです」一覧と集合場所表示のみ）を作り、1 イベントで実地投入
- **事前に決める成功基準（案・着手前に確定させること）**:
  - 1 イベントで「ひとりです」発信（または目印への合流）10 人以上
  - 発信者のうち 50% 以上が実際に誰かと合流
  - 未達なら: 課題インタビュー（interviewing スキル併用）で「なぜ使わなかった／動けなかったか」を掘り、ソリューション形態（例: マッチングではなく主催者向けの卓割り支援へ）のピボットを検討
- **判断**: 2 イベント連続で基準を満たせば本開発へ。複数回ピボットしても行動が起きなければ、個人開発として「自分の 1 イベントを楽しくする道具」に目的を縮小するのも正当な結論。

## 6. 品質チェックの自己点検（残課題）

- 課題起点・代替手段の明記・競合表への代替手段包含: 済
- TAM/SAM/SOM: ユーザー数ベースで根拠付き概算（統計の出所は仮定を含む。精緻化するなら market-competitor-analysis の領分）
- 未検証事項: 課題の深刻度の定量裏付け（当事者ヒアリング未実施）、密度仮説の成立条件、話題カードの有効性
- 次工程: MVP 検証 →（手応えがあれば）prd-writing で仕様化、persona-journey-design でペルソナ肉付け
